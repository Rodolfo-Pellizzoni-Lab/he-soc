Memory-Tagged QoS on AlSaqr

A memory bandwidth cap is only as good as the tag on each request. Giving the kernel a QoS ID of its own, as AMD PLZA does, is not enough: it fixes one failure and opens another. This report shows where each tagging policy fails on real hardware and which one holds.

Stock: 80 %of its solo bandwidth is what the victim keeps next to a tightly capped tenant. The tenant's timer ticks are throttled and stall the kernel for 28 to 61 ms.
PLZA: 22.2 MB/sof traffic from a tenant capped at 9.4, made through system calls. It is all charged to the kernel, and the victim drops to 60 %.
Selective: 15.5 MB/sfrom the same tenant doing buffered writes. Kernel threads do the copies later under the kernel's ID.
Selective + tag: 9.1 MB/sin that case, and at or under the cap in every case tested. The victim keeps 85 to 99 %.

The memory regulator

Every memory request from a core carries a tag: a control ID (RCID), which says whose budget it spends, and a monitoring ID (MCID), which says whose counter it adds to. Linux sets the tag per task through resctrl, so a resctrl group is an RCID.

The regulator sits inside the last-level cache (LLC), on the path from the cache to DRAM. Only cache misses and write-backs reach it, so it regulates real memory traffic and leaves cache hits alone.

The rules it applies

  • Period and capacity. Time is cut into periods (1 ms here). The capacity is how many bytes may go to DRAM per period: 47,000 bytes, which is 47 MB/s.
  • Reservation (MB_MIN). A share of the capacity that a group is guaranteed. A request inside its group's reservation goes ahead of everything that is not.
  • Weight (MB_WGHT). What is left after reservations is shared between groups in proportion to their weights.
  • Hard limit. Weight 0 means the group gets its reservation and nothing more. This is the cap used throughout this report: MB_MIN 205 with weight 0 is 9.4 MB/s.
  • Counting. Bytes sent to DRAM are counted per MCID. The "who is charged" charts below read these counters.

How a capped group is kept from slowing the others

  • Parking off the main path. A miss that may not go yet waits in a 16-entry pool. The requesting core stalls on that load; other groups' requests pass it.
  • Smooth release. A reservation is earned at a constant rate across the period, so a capped group cannot take every DRAM slot at the start of each period.
  • Exact line locks. A parked request keeps its cache line locked. The lock table is exact, so the lookup stage waits only for lines that really are locked.
  • Writes and device traffic. A write buffer and admission gates on the DMA ports keep a throttled writer or device from holding the shared path.

The register interface follows the RISC-V CBQRI specification, so the Linux resctrl driver drives it with MB_MIN and MB_WGHT files.

Baseline: the cap itself isolates

When the tenants are plain user-mode readers and privileged code has IDs of its own, the victim keeps 27.2 of 28.2 MB/s next to three readers capped at 9.4 MB/s. On bare metal it keeps 99 to 100 %. Everything the victim loses in the rest of this report comes from how privileged work is tagged.

Which ID should privileged work carry?

Stock resctrl changes a core's ID only on a context switch, so kernel and firmware work runs under whatever task happens to be on the core. AMD's PLZA and Arm's MPAM can give kernel mode its own ID, but the setting is all or nothing. Neither answer is right for every kind of privileged work.

The four policies

AlSaqr's cores extend Ssqosid with an ID per privilege level. Machine mode has one, set at boot. Kernel mode has one in a register (hqosid) that the kernel itself may write, which makes the kernel's policy a pure software choice. A patch to the 7.2 kernel adds a runtime switch, so all four policies are measured on the same boot and the same hardware.

  • Stock. Kernel work carries the running task's ID.
  • PLZA. All kernel work carries the kernel's ID.
  • Selective. The kernel's ID by default. Inside a system call or a page fault the caller's ID. An interrupt that arrives there switches back to the kernel's ID until it returns.
  • Selective + tag. As selective, and every queued work item records the ID of the task that queued it. The worker thread runs the item under that ID. A worker that queues further work passes the tag on, so a chain of workers keeps its origin.

  • Stock fails when system work lands on a capped core. With a user-mode tenant at a tight cap, its timer ticks are throttled with it. The victim stalls for 28 to 61 ms and keeps 80 %, and the tenant gets a fifth of its allowance.
  • PLZA fails when the kernel works for the tenant. With system calls or page faults, all of the tenant's traffic is charged to the kernel's group. The cap does nothing and the victim drops to 60 %.
  • Selective fails when the work is deferred. With buffered writes, kernel threads do the copies later, outside the system call. Stock, PLZA and plain selective all let 15 to 19 MB/s through a 9.4 MB/s cap.

With memory as the bottleneck

In the runs above the board's DDR4 was not a bottleneck. Four readers together got 107 MB/s, so an uncapped neighbour cost the victim almost nothing, and a tenant that escaped its cap took little from anyone. To show contention at the memory itself, these runs turn on the DRAM timing model, which holds each response until a slower, modelled memory would have delivered it.

The setting is a latency of 100 cycles and 20 cycles per 8-byte beat, a 20 MB/s memory bus. It is the first setting tried where memory clearly limits the cores and the model reports no late reads, meaning the real memory always answers before the modelled time.

The regulator's capacity is set to 17 MB/s, just under what the modelled bus sustains, and the tenant's group is hard-capped at 20 % of it, 3.4 MB/s. The victim alone reads 8.45 MB/s.

  • The cap works for readers. The victim keeps 79 % next to uncapped readers and 95 % once they are capped.
  • PLZA's escape now costs the victim half its bandwidth. The system-call tenant sends 10.4 MB/s under the kernel's ID, three times its cap, and the victim keeps 47 %. With selective + tag the tenant stays at its cap and the victim keeps 78 %.
  • Deferred work needs the tag. With plain selective, more than half of the buffered-write tenant's traffic goes out under the kernel's ID and the victim keeps 60 %. With the tag it keeps 74 %.
  • Writes are the largest remaining loss. Uncapped writers leave the victim 29 %; capped, 71 %, against 95 % for capped readers. A written line needs a read and later a write-back on the same bus, and the write-back is charged to whoever evicts the line. This is a gap in the cache, described under the limits below, and it is why even the best policy stops at 74 to 78 % for tenants that copy.

The same failure one level down: firmware

The stock failure does not stop at the kernel. With the kernel on its own ID and three readers at the smallest cap, the victim still lost about 10 %, with stalls of tens of milliseconds. On bare metal it lost nothing.

We halted all four cores over JTAG at random moments during the run and recorded where each one was. The capped cores were inside OpenSBI, the machine-mode firmware, in about a third of the samples.

Firmware work on a core (timer interrupts, the emulated time register, calls from the kernel) carried the ID of whatever task was running there. On a capped core each firmware cache miss then waited about 4 ms. Much of that work happens inside kernel critical sections, so the other cores waited on the lock. Giving machine mode its own ID removes the stalls. An association for kernel mode alone, which is what PLZA offers, leaves this open on a system with a firmware layer below the kernel.

Limits of the evidence

  • Sample size. Most bars are one or two short runs. Differences of a few tenths of a MB/s are noise. The memory-bound set is missing the stock policy and the page-fault tenant.
  • Dirty lines are charged to whoever evicts them. Next to capped tenants that write, the victim keeps 82 to 89 %, against 97 % next to a capped reader (fast memory; 71 % against 95 % when memory is the bottleneck). A user-mode writer and a user-mode copy give the same loss as the system-call tenant, so kernel tagging is not the cause. The cache writes a dirty line back under the tag of the request that evicts it. The victim's group is charged 28 MB/s while the victim itself reads 23: about 5 MB/s of the tenant's write-backs are paid from the victim's traffic and never count against the tenant's cap.
  • Smallest cap under selective. At 0.05 MB/s the victim gets 25.2 to 26.0 MB/s under selective against 27.3 under PLZA, with stalls of 20 to 48 ms. The cause is not found.
  • Shared deferred work. A tag follows the first task that triggers a shared writeback pass. Two tenants writing through the same device would be mixed. Here each tenant had its own loop device.
  • I/O. Device interrupts and completions are not attributed to the task that issued the request. They run under the kernel's ID.
